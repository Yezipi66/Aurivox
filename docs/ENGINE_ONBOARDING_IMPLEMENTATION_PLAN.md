# 引擎接入 · 实施计划（2026-10-09 起草）

> 分支：`research/engine-onboarding-complexity`
> 依据：[`ENGINE_ONBOARDING_RESEARCH_CONCLUSION.md`](./ENGINE_ONBOARDING_RESEARCH_CONCLUSION.md)
> 口径：`[实测]` = 本机跑出来的 · `[读码]` = 读代码得出 · `[待裁]` = **还没定，别当结论用**
>
> ⚠️ **本文件是提案，不是决议。** 每一批都标了「谁做」和「要不要 Owner 点头」。

---

## 0. 目标（一句话）

**让「接一台新引擎」从「手写 46 个字段」变成「确认一份自动生成的草稿」。**

约束（不可违反）：
- ⛔ **不损害模型能力** —— 名片漏一个参数 = 用户永远看不到它（平台不兜底）
- ⛔ **平台是传话筒** —— 不校验、不判断、不替引擎补默认值
- ⛔ **`lib/` 的四个文件不许出现引擎名**（`registry.js` / `payload.js` / `profile.js` / `web/src/lib/engines.js`）

### 第 1 批 · 参数提取多源合并（难点一）

**要解决**：反射只看得到签名参数；GSV 类 dict 引擎反射只给 2 个（真实 27 个）。

| | 内容 |
|---|---|
| **scope** | 新建 `tools/dev/extract_params.py`（多源合并）+ 在向导里接一条链路 |
| **四个源**（`[实测]` 覆盖能力见结论文档 §2） | ① 反射（签名）② CLI argparse（AST 静态解析）③ 源码取值点（`inputs['xxx']`，AST）④ docstring / README 表 |
| **合并规则** | 按参数名合并；**每个参数标来源**；冲突时**不自动裁决**，两个都列出来 |
| **⛔ 硬约束** | 只产**草稿**，标 `_needs_review`；⛔ 不写进 `models.required` 那种「人确认过的」位置 |
| **文件** | 新建 `tools/dev/extract_params.py` + `tools/dev/test/`（或挂在现有 test 下） |
| **验收** | ① 对 index-tts 跑：反射 25 + CLI 31 合并后 **≥31**（去重后）<br>② 对 GSV 跑：**能挖出 dict 里的 27 个键**（现在反射只有 2）<br>③ ⭐ **变异**：把源码取值点解析去掉 ⇒ 必须有测试变红（否则这条没在守）<br>④ 每条参数带 `source_detail`（哪个文件、哪种源） |

⚠️ **风险**：`[实测]` 已踩到 **README 表假阳性**（把模型排行榜当参数表）。
⇒ 必须有表头判定 + 排除名单，且**宁可漏也不能误报**。

### 第 2 批 · 映射助手（难点二）

**要解决**：从"参数名"到"平台词"的翻译 —— 这是唯一必须人做的部分。

| | 内容 |
|---|---|
| **scope** | 从提取到的参数里，**给出平台词候选**（不是替用户决定） |
| **判据** | `[实测]` 名字线索是**弱证据**（`spk_audio_prompt` → audio、`emo_vector` → number[]）<br>⛔ 但**语义别名不可自动映射**（`--fp16` ↔ `use_bf16` 近义非等价，会静默出错） |
| **做法** | 平台词候选按「名字线索命中」排序，**人从中选**；选完写进名片的 `maps` / `call.bind` |
| **文件** | 新建 `tools/dev/map_assistant.py`（或并入第 1 批） |
| **验收** | ① 对 CosyVoice2 跑：`tts_text`/`prompt_wav`/`prompt_text` 应被提示为 text/reference_audio/reference_text 候选<br>② ⛔ **不自动写入名片** —— 只给候选，落盘要人点 |

#### ⚠️ `[待裁]` 是否扩充平台词

`[调研]` 必传映射率 ≈81%，缺口集中在 `speaker`：

| 建议新增 | 解决 | 代价（`[读码]`） |
|---|---|---|
| **`speaker`** | CosyVoice2 `spk_id`、MeloTTS `speaker_id`、OpenVoice `speaker`、Kokoro `voice`（**4 台**） | 改 `payload.js:48-50`（**只有一份定义**）+ 前端 + 守卫测试 |
| `source_audio` | CosyVoice2 VC 的 `source_wav` | 同上 |
| `instruct_text` | CosyVoice2 Instruct | 同上 |

**要你裁的是**：
- 加不加？（不加的话那 4 台引擎的必传参数只能作为"引擎私有参数"透传，不能走平台词）
- 加的话加几个？（我倾向**只加 `speaker`** —— 它解决 4 台，性价比最高）

⚠️ 注意：`payload.node.test.js` 用**真名片做夹具**（`resolveEngineProfile('gpt-sovits')`），
而"四个文件不许出现引擎名"那条纪律由 `registry.node.test.js` / `profile.node.test.js` 守着。
⇒ 加平台词要同时跑这两个守卫 + `payload.node.test.js`，是**契约变更**。

### 第 3 批 · 草稿展示与引导（难点三）

**要解决**：映射不上的参数，怎么让用户填对。

| | 内容 |
|---|---|
| **scope** | 名片表单里每个字段显示「格式 + 例子 + 填错会怎样」 |
| **⛔ 必须守住的边界**（`[调研]` 结论） | 平台只做「名片 → UI」的机械翻译：<br>名片写了 `choices` 就画下拉、写了必填就画标记<br>⛔ **不解释、不补全、不校验** |
| **数据来源** | `[读码]` **`profile.js` 每条抛错本身就写着"应该写什么"** ⇒ 把已有文案提到字段下面（**搬运，不是新写**） |
| **文件** | `tools/engine-wizard/core/fieldmeta.js`（补 `format`/`example`/`onError` 三件套）<br>`tools/engine-wizard/editor/ManifestForm.jsx`（渲染） |
| **验收** | ① 每个必填字段下方能看到「填什么格式 + 例子」<br>② 至少 3 个字段的「填错会怎样」来自 `profile.js` 的现有抛错文案（可 grep 对上）<br>③ ⛔ **没有新增任何平台侧校验** —— 判据：`git diff` 里 `lib/engines/profile.js` 只有注释改动或零改动 |

## 3. 明确不做（本轮）

| | 理由 |
|---|---|
| **加 SHA 校验字段** | 会动 `models` schema 磁盘格式 ⇒ 要走 C11 豁免论证，**别顺手做** |
| **`--help` 解析器（N6）** | `[实测]` 与反射互补不替代；且 4 台里 2 台没 CLI ⇒ 收益有限，**先做多源合并** |
| **改 `lib/` 的四个文件** | 除了第 2 批那个 `[待裁]` 的加词 |
| **第 5 步（verify）** | 已有独立计划（`ENGINE_ADOPTION_FLOW.md` §四），**不混进本轮** |
| **环境缺陷 3（进度文件脱钩）** | 已记录在 `ENGINE_ENV_DEFECTS_2026-10-09.md`，**单独一刀** |

## 5. 每批的验收纪律（照项目现有规矩）

3. 每条能力配**变异测试**（改坏它，必须变红）

## 6. 本计划的不确定处

1. **第 1 批的"四个源合并"** 是设计，**未实现** —— 合并规则（冲突怎么办）是纸面推演
2. **第 2 批的候选排序** 依据是名字线索，`[实测]` 它是**弱证据**（16 个 call 参数里 8 个类型 unknown）
3. **第 3 批** 说"搬运 `profile.js` 的抛错文案"，但**没逐条数过**有多少条能直接搬
4. **`[调研]` 的 81% 映射率** 只抽验了 2 台，其余 12 台未核实
5. **批次顺序** 是按依赖推的，**未与 Owner 讨论过**
