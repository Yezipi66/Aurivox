# 注释规范

注释写给下一个读代码的人。他手里只有代码，没有聊天记录、没有提交历史、没有本文件以外的文档。
注释要回答的只有一件事：**这段代码现在做什么，以及哪些地方不看注释就会改错。**

示范文件（按本规范重写过注释，代码逐个 token 未变）：

- `lib/engines/residency.js`
- `lib/engines/launchPlan.js`
- `web/src/lib/modelPickers.pure.js`
- `web/src/lib/engines.js`

## 八条规则

1. **只写现在，不写历史。**
   不写「在它出现之前」「搬家前」「第一版是……后来……」「已被否决」。
   历史写进提交信息；做过的决定写进 `docs/` 的决策文档。代码一改，历史注释就会说错话。

2. **不写谁说的、谁定的。**
   不引用户原话，不写「我做不到」「我验不了」「被判小学生」「使用者反馈」。
   注释没有作者视角，只陈述代码的事实和约束。

3. **不引用行号。**
   不写 `xxx.js:337`、`第 239-243 行`、`start.ps1:149`。行号一改就错，读者会被带到错误的位置。
   要引用就写文件名加函数名：`supervisor.js 的 planAdmission 调用处`。

4. **注释必须离开文档也能读懂。**
   可以在末尾挂一个指引（`契约 §5.8`），但句子本身要把规则说完整。
   不写只有内部编号的句子（「理由同 C12」「A 那件事」）。

5. **只写代码表达不出来的东西。**
   值得写：非显而易见的约束、两个看似等价写法之间的取舍、改错后会静默出错的地方、和别的文件必须保持一致的约定。
   不值得写：函数名已经说清楚的事（`/** 字段说明，可以为空。 */ function fieldHelp`）、逐行翻译代码。

6. **一件事只说一遍。**
   同一条理由（例如「静默失败最难排查」）不要在每个函数上重复；写在最靠近它生效的地方一次。
   文件头写整个文件共用的前提，函数上只写这个函数特有的。

7. **不写会过期的测量值。**
   「GSV 峰值 3547MB」「16G 机器只剩 6230MB」属于测试夹具或文档，不属于注释。
   注释可以写量级和方向（「每 8G 一台」），不写某一次的读数。

8. **短。**
   文件头 2 至 5 行：做什么、关键前提、不能做什么。函数注释通常 1 至 2 行。
   单文件注释占比不超过 20%，力争 15%。超过时先检查是否违反了第 1、2、6 条。

   文件头放在文件最前面，在 import 之前（仓库里 453 个文件这样写，40 个不是）。
    放在 import 之后就不叫文件头了——读者打开文件先看到的是依赖，不是这文件干什么。

## 风格与可读性

八条规则管住「不写什么」。这一节管住「写成什么样才读着顺、全仓一致」——可读性本身是规范的一部分，不是各写各的。改注释时顺手统一，不在单独一次大扫除里才做。

### 标点与排版（宽松）

- 中文注释用全角标点，英文标识符与路径保持半角。
- 句子结尾不一定要句号；同一段注释里别一会儿带、一会儿不带就行。
- 标点不做机器校验：`{a, b}` 里的半角逗号是代码不是散文，`foo.js：` 后面用全角冒号引出说明也没问题。这类半/全角混用机器判不准，抓死了只有噪音。标点不对是小事，改得顺手就带上，不必专门扫一遍。

真正要守的是下面这一节。

### 注释不是草稿纸

注释里只能有代码的事实与约束。下面四类东西，再顺手也不能留在注释里：

| 类别 | 不这样写 | 这样写 |
|---|---|---|
| 归属与决策 | 「按产品要求用英文显示」「Owner 裁决这样定」 | 「这行固定用英文显示」——只留结论，不留人、不留过程 |
| 变更史 | 「原来 tier 在行内、phase 在行内，用户要在三个地方回答同一个问题」 | 「三者分开会让同一个问题被问三遍」——讲现在的坏处，不讲过去的形状 |
| 备忘待办 | 「TODO(骨架)：再加一档固定值」 | 「固定值那一档不在这一列里」——没做就是没做，留在注释里只会烂掉 |
| 人称与口吻 | 「接线规则是用来提前发现错误的，不是用来刁难人的」 | 「接线规则是为了在连线时就把接错的地方报出来」 |

判定要点：说**数据**时可以写「原来的设置」「原来的版本号」（那是运行时的旧值，不是代码历史）；
说**界面与结构如何演变**时写「原来 XXX、现在 YYY」就是 changelog，删。

决定写进 `docs/` 的决策文档，变更写进提交信息，待办写进 issue。注释一旦记了这些，
代码一改它就过期，而且没人会回来更新它。

### 一句一意

- 一个注释块只讲一件事；需要多句时，每句一个完整意思，不堆成一段流水账。
- 两句话以上才考虑分段；一段里塞五六个「因为／所以／另外」会让人读不进去。

### 不写废话词

删掉不增加信息的填充词：`其实`、`说白了`、`简单来说`、`总的来说`、`也就是说`、`换句话说`、`顺便`、`老实说`、`注意一下`、`说实在的`、`换言之`、`讲白了`、`说穿了`、`总之`。`这里`、`这个`、`上面`、`下面` 只在离开它就指不清代码位置时才留；「这个函数这里先……」里的「这里」多数可删。

### 术语统一

同一概念全仓一个词，不换着叫，也不与代码里的命名打架：

| 概念 | 用这个词 | 不这样叫 |
|---|---|---|
| 引擎配置 | 名片（manifest） | 配置、设置、spec |
| 平台与引擎的约定 | 契约 | 协议、规约（特指时可用「约定」） |
| 字段必要性 | 必填 / 可选 | 必须、必要、强制 |
| 常驻策略 | 预热 / 按需启动 / 空闲释放 | 常驻、保活、懒加载（除非代码里就是这词） |

### 代码即名，注释不复述

函数名、变量名、类型已经说清的事不重写一遍；注释只补代码表达不出的 WHY 与约束。这条与第 5 条同源，单列是为了强调：复述代码的注释既占地方，又制造「代码改了、注释没改」的错位。

### 改前改后（可读性）

改前：

```js
// 这个函数这里先判断一下，如果它是 common 的话，就走 common 的那条路，
// 说白了就是 common 不用单独起进程，换句话说 common 是平台自己管的。
```

改后：

```js
// common 由平台自己管理，不单独起进程，所以走 common 这条路径。
```

改前：

```js
// 返回的是个对象，里面有 name 和 path 两个字段，name 是名字，path 是路径。
function describe(f) { /* ... */ }
```

改后（函数名已说清，删掉）：

```js
// 把文件描述成 { name, path }，供上层列出。
function describe(f) { /* ... */ }
```

### 自查清单（提交前过一遍）

- [ ] 有没有把谁定的、哪次改的、以后要做的写进去？（决策 → `docs/`，变更 → 提交信息，待办 → issue）
- [ ] 一条注释是不是只讲一件事？
- [ ] 同一个概念，这个词和别处、和代码命名一致吗？
- [ ] 删掉它，意思会变模糊吗？（不变就删——复述代码的注释也算）

跑 `node tools/dev/audit-comment-style.cjs` 可以机械筛出「决策 / 变更史 / 待办 / 人称」四类嫌疑，
默认跳过测试文件；它是筛子不是法官，报出来的要自己判一眼。

## 改前改后

### 历史叙事 → 当前约束

改前：

```js
// 这个文件在还的账，那个账的原话是：
//    「接入 IndexTTS3、4、5，我一次启动是不是要启动 4 台引擎，
//      这个是工程该有的思维吗？」
//    今天启动脚本的行为是「engines\ 下装了几台就起几台」。而其中一台
// 开进程那一刻就吃掉约 6G 内存（还没合成一个字）。……
```

改后：

```js
// 引擎常驻策略：开机预热、按需启动、空闲释放、启动前内存检查。纯计算，不认识具体引擎。
// 判据是模型位的 applies_at（契约 §5.8）：有 launch 位的引擎进程即占内存，按需启动、
// 空闲释放；只有 call 位的可预热、不释放。
```

### 行号引用 → 符号引用

改前：

```js
// 端口非法 ⇒ 不在这抛……让外层
// buildLaunchPlan 统一报 ENGINE_LAUNCH_PORT_INVALID（第 239-243 行）。
```

改后：

```js
// 端口非法时不在这里报错，交给 buildLaunchPlan 报 ENGINE_LAUNCH_PORT_INVALID。
```

### 长篇论证 → 一句结论加一个理由

改前（16 行，含「被判小学生」「事实留，说明走」等）：

```js
// 悬停只留底模目录那一行。
//
// 进程状态那段被判「小学生」，……
```

改后：写在函数上方一处：

```js
// 顶栏引擎徽章，只显示最需要处理的一项：底模缺失（红，唯一的红色）> 启动中 > 合成中
// > 运行中 > 待命（灰，按需启动下未运行是正常的）。悬停只显示底模目录和正在载入的模型。
```

### 值得保留的注释长什么样

```js
// 必须是 >= 0：0 表示不占内存，不能落入 null（未知）一支。
const need = Number.isFinite(state.needMb) && state.needMb >= 0 ? state.needMb : null
```

一行，说清楚「为什么不能改成 `> 0`」。这是改错后会静默出错、而代码本身看不出来的地方。

## 动手前自查

- 删掉这条注释，下一个人会改错吗？不会就删。
- 这条注释三个月后还对吗？依赖行号、读数、某次对话的，都会错。
- 不打开任何文档，这句话读得懂吗？

## 只改注释时如何证明没动代码

比较改前改后去掉注释后的 token 序列，必须完全一致：

```bash
node -e "
const {parse}=require('@babel/parser');const fs=require('fs');const cp=require('child_process');
const f=process.argv[1];
const t=s=>parse(s,{sourceType:'unambiguous',plugins:['jsx'],tokens:true}).tokens
  .filter(x=>x.type!=='CommentLine'&&x.type!=='CommentBlock')
  .map(x=>(x.type.label||x.type)+':'+JSON.stringify(x.value));
const a=t(cp.execSync('git show HEAD:'+f).toString()),b=t(fs.readFileSync(f,'utf8'));
console.log(JSON.stringify(a)===JSON.stringify(b)?'same':'DIFF');
" path/to/file.js
```

注意：JSX 里的 `{/* */}` 注释会产生花括号 token，删除它会让比较报 DIFF，需人工确认。
